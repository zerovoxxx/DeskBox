# DeskBox 1.5.7.1

Fork maintenance release based on upstream `v1.5.7` (`61f151f3e018e109f8bb6faa593510a23d7d0f95`).

- Includes the upstream 1.5.6 and 1.5.7 updates, including reliable process shutdown, display placement, layout recovery, and theme fixes.
- Preserves the owned tray menu window used to avoid shell-dependent windowing calls during Windows logon. The owned window retains startup retry and native-menu fallback behavior.
- Preserves persisted shortcut icon resource recovery, extensionless ICO decoding, and retry handling for transient icon failures.
- Preserves the fork's commit identity enforcement and Windows UNC build-script fixes.
- Local validation reuses the existing .NET SDK 10.0.303 through explicit SDK resolver overrides; the repository retains the upstream SDK pin and package lock versions.
- Repository contract tests normalize checkout line endings and honor explicit SDK resolver overrides for child processes.

The local x64 installer uses the repository's framework-dependent workflow with `SelfContained=false` and `WindowsAppSDKSelfContained=false`. It installs over the existing DeskBox installation and uses the required .NET and Windows App Runtime dependencies.

## Validation

- x64 Debug build and Release publish succeeded using the existing SDK 10.0.303.
- Full x64 suite: 5,411 passed out of 5,412. The remaining test, `AotAudit_RejectsArm64BeforeResolvingToolsOrTouchingArtifacts`, failed because Windows antivirus blocked the audit script with `ScriptContainedMaliciousContent`; it was reproduced independently, and security settings were preserved.
- NuGet vulnerability audit reported no known vulnerable packages.
- In-place upgrade from 1.5.6.1 succeeded. All 168 installed payload files matched the published SHA-256 hashes, and existing application data was unchanged before first startup.
- Startup completed with zero failed or degraded steps. All nine widget identities, names, positions, sizes, mapped directories, and the existing group were preserved. Existing preferences were preserved apart from the schema migration from 9 to 14 and the update-check timestamp.
- The existing scheduled startup configuration remained enabled. An actual Windows reboot/logon was not performed.
