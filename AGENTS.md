# DeskBox development workflow

- Every merge/update delivery must finish with a current Release installer and an in-place upgrade of the user's existing installation, unless the user explicitly asks for source-only work or to skip installation. Updating a shortcut to a repository Debug executable does not count as an upgrade. For this machine, re-detect the registered installation before each delivery; the current all-users installation is `D:\Program Files\DeskBox`.
- Before an upgrade, record the merged commit, source changes, installed version/scope/path, exact running executable paths, desktop/Start-menu/pinned shortcuts, and every DeskBox startup entry (scheduled tasks, HKCU/HKLM Run, and Startup-folder shortcuts). Preserve the user's startup enabled/disabled preference, settings, layouts, Todo/Quick Capture content, and managed files. Do not uninstall or reset user data to solve an upgrade.
- Build the normal Direct x64 retail package from the merged source: run `scripts/publish-aot-retail.ps1 -Platform x64 -DotNetPath <verified SDK host>`, then compile `installer/DeskBox.iss` with Inno Setup using `/DDeskBoxNativeAot=1 /DDeskBoxBundledRuntime=1 /DMyAppReleaseDir=<this run's publish directory>`. The current retail format is smoke-free Full Native AOT with bundled Windows App Runtime, as enforced by that script. Use matching `Platform=x64` and `RuntimeIdentifier=win-x64`; keep `DeskBoxAotSmokeHarness=false`. Do not replace the retail workflow with Debug, a smoke/audit build, or an arbitrary old publish directory. For a public dual-architecture/Store release, follow the full `scripts/build-stage-7c1-distribution.ps1` distribution gate instead.
- Use a fresh, isolated build/output directory or preserve existing artifacts before a script clears its fixed output. Verify source/installer/payload versions agree, the Release executable was written after this publish started (Native AOT has no `DeskBox.dll`), required native/runtime files and `DeskBox.InstallManifest.txt` are present, and the installer SHA-256 is recorded. Run the complete x64 test suite; only a non-aborted run with passed count equal to total count is green. An installer file existing or a zero-error build alone is not delivery acceptance.
- Stop DeskBox processes by verified executable path before replacing the installation. Upgrade with the newly built installer in the existing registered install scope and directory. Let the installer perform its manifest-based stale-payload cleanup; do not manually wipe the installation or unrelated output packages. Retain the installer and its install log.
- After installation, repair and read back all existing DeskBox launch shortcuts, and create the requested desktop entry, so they target the installed Release executable with the installed directory as working directory. No everyday shortcut or enabled startup entry may target `bin/Debug`, a repository/share build, a staging directory, or an old installation. Remove or replace only verified DeskBox duplicates; preserve unrelated entries. Check the uninstall registry version and install metadata as well as the executable version/hash against this run's payload.
- Validate the real startup route: with startup enabled, stop the current DeskBox instance, trigger its existing startup task/entry, then verify exactly one DeskBox process runs from the upgraded installation with the expected version. Also launch the desktop shortcut and verify it activates that same installed instance without spawning an old copy. Check fresh startup logs for failed/degraded stages and data-schema rejection. Report the installer path, installed version/path, shortcut target, startup target, and verification outcome. If installation, shortcuts, or startup verification is unfinished, say the update is incomplete and continue resolving it; do not hand it off as a successful update.
- The Debug restart rules below apply to ordinary development edits only. A merge/update or formal-package delivery must end with the installed Release instance, and must not switch the user back to Debug after acceptance.
- After changing application code, first stop any running `DeskBox.exe` whose executable path is under this repository, then build the affected project, and start a fresh instance from the current Debug build unless the user explicitly asks not to restart it. Stopping before the build avoids locking the output executable. A running instance can also make the build silently skip writing its output while still reporting zero errors, so a successful build is only proven by the canonical `DeskBox.dll` write time being newer than the build start (the exe host is a fixed stub); verify this timestamp after each build. An installed copy holds the single-instance lock and makes the repo Debug exe exit silently — stop it by executable path, possibly twice.
- The canonical local development executable is `src/DeskBox/bin/Debug/net10.0-windows10.0.22621.0/DeskBox.exe`.
- After starting DeskBox, verify that exactly the intended repository build is running and report the executable path.
- Do not launch DeskBox from `Output`, `artifacts`, `.artifacts`, or `src/DeskBox/AppPackages` unless the user explicitly requests testing a packaged or published build.
- Preserve unrelated user changes and release artifacts. Ask before deleting material output directories or installer packages unless the user explicitly authorizes their removal.
- DeskBox is a packaged Windows application. Do not first run its tests with the default `AnyCPU` platform: MSIX packaging rejects a processor-neutral app-host executable. Run the test suite directly with `dotnet test .\tests\DeskBox.Tests\DeskBox.Tests.csproj --no-restore --verbosity:minimal -p:Platform=x64` (add `-p:RuntimeIdentifier=win-x64` when using architecture-specific restored assets). A test run only counts as green when the passed count equals the total count — an aborted run also prints `失败: 0`.
- For Release publishing, always specify a matching platform and runtime identifier from the start: `-p:Platform=x64 -p:RuntimeIdentifier=win-x64` for x64, or `-p:Platform=ARM64 -p:RuntimeIdentifier=win-arm64` for ARM64. The current Full Native AOT retail workflow sets `SelfContained=true` and `WindowsAppSDKSelfContained=true` through `publish-aot-retail.ps1`. Use `SelfContained=false` and `WindowsAppSDKSelfContained=false` only when the user explicitly requests the legacy runtime-download installer workflow.
- The explicit architecture rules above apply to tests and Release publishing. Continue using the canonical non-platform Debug output for the normal local restart workflow.
- When the root cause you diagnosed calls for a deeper fix than the one you are about to implement (a bolt-on guard around a broken mechanism), stop and present the trade-off — root cause, shallow fix with its debt, root fix with its cost — and let the user decide. Never silently choose the shallow path to save time or tokens; an emergency hotfix is allowed only with an explicit debt record in the handoff.
- Commits and PRs carry only the user's identity (`zerovoxxx <48088758+zerovoxxx@users.noreply.github.com>`). Do not add `Co-Authored-By` trailers, `Generated with` lines, or any assistant/tool attribution to commit messages, PR bodies, or code comments. The tracked `.githooks/commit-msg` hook enforces the author and committer identity and rejects attribution trailers; the CI `Commit message attribution check` rejects those trailers in PRs. On a fresh clone, run `git config core.hooksPath .githooks`, `git config user.name zerovoxxx`, and `git config user.email 48088758+zerovoxxx@users.noreply.github.com`.
